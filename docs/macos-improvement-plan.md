## 决策摘要

1. **先修结算。** 当前复现了「杀」因缺少目标返回失败，牌却进入弃牌堆。对局界面还绕过了 `TurnManager` 现成的「乐不思蜀」跳过出牌逻辑。先完成这两项和武将翻面，再改善表现层。
2. **首个体验版本做一键练习。** 在现有 2 人单机对局和简单 AI 上增加固定练习预设，设置页继续提供 2–8 人身份局。交付完整键盘流程、当前合法动作和清晰的结算结果。
3. **战报先行。** 先让玩家能查看上一局和导出可诊断的事件记录。已有存档缺失摸牌堆顺序等关键信息，继续游戏单独排期。
4. **联机分阶段启用。** 单机验收后可启动局域网内测。对局动作、房间座位和玩家可见信息要通过两个真实客户端验证。公开服务器是后续发布决定。

首批「规则正确、可安全构建」估算 **5–8 人日**。单机方案合计 **12–19 人日**，适用于一位熟悉 Python 的开发者，含回归与 Mac 验收。范围包括现有核心牌型和已指定的练习场景。局域网联机预研及内测另估 **7–12 人日**，在单机动作接口确定后复估。所有工期为实施估算。

### A. 回合与动作正确性

**实施。** 先为「乐不思蜀」「翻面」「无目标的杀」补失败用例。令 `TurnManager` 负责阶段推进、跳过规则和阶段事件。复用其现有 AI 出牌路径，通过已有 `RequestHandler` 与 Textual 桥接接入需要真人操作的出牌及弃牌步骤。保留现有 worker，UI 线程负责渲染、收集选择和取消。首个版本让 `GamePlayScreen` 的真人、AI 入口共用阶段判断，待实际对局测试覆盖后逐一收敛其手动推进分支。

出牌从 `actions.py`、`engine.py`、`combat.py` 和 `effects/` 的真实调用厘清提交点。先验证当前阶段、牌归属、目标和次数，再进入费用或卡牌移动。首批修「杀」、满血的「桃」、无合法目标的单目标锦囊和「铁索连环」重铸。对已经合法打出、后来被「无懈可击」抵消的锦囊保持正常出牌及弃牌语义。当前牌名或对象地址不足以作为跨请求标识。阶段内的选择由待处理请求提供可用牌和目标标识。

在真人出牌、目标选择、响应和弃牌中引入明确的请求编号与完成结果。用现有 modal 回调完成仍有效的请求，消费结果时结束计时及等待。退出应关闭当前弹窗并唤醒 worker。按失败原因区分非法动作、玩家取消以及超时采用的游戏规则。

**改动文件。** `game/turn_manager.py`、`game/engine.py`、`game/actions.py`、`game/combat.py`、`game/request_handler.py`、`ui/textual_ui/screens/game_play.py`、`ui/textual_ui/bridge.py` 及相关用例。按阶段分 PR，不把技能 DSL 或所有锦囊一起改写。

**验收。** 固定判定牌验证「乐不思蜀」命中后能摸牌且无法出牌、随后进入弃牌，翻面只跳过一次并翻回。失败出牌前后手牌、装备、牌堆、弃牌和回合次数相同。合法被「无懈可击」抵消时牌进入弃牌区。迟到的按键和回调无法完成下一次请求。出牌、选目标和弃牌等待中的退出均结束后台线程。引擎用例与实际 TUI 对局都覆盖上述分支。

### B. Mac 构建和发布验收

**实施。** CI、Docker 和 PyInstaller 装同一个项目发行包或从同一份 `pyproject.toml` 解析。Mac 构建用独立 staging 路径运行 `build.py`，先保留已验证产物，再写新的带架构和版本标识产物。Release 用实际架构验证及从源码目录外启动的冒烟测试作为门槛。将 Ruff 固定到 CI 和本地使用的同一版本，记录现有问题，先在独立改动中处理阻塞打包的检查，不进行全库格式化。

**改动文件。** `build.py`、`pyproject.toml`、`requirements.txt`、`.github/workflows/{ci,release}.yml`、`Dockerfile` 及 `README.md`。按本机 Mac 和共享发布流程分别提交。现有 Windows 成品保存在原路径。

**验收。** 干净虚拟环境安装 wheel，`pip check` 通过，能加载卡牌、武将、两种语言和 TCSS。Apple Silicon 成品通过 `file`、签名校验，并在真实终端从主菜单进入一局现有身份局，执行合法出牌、结束回合和退出。完整练习局在 C 验收。记录产物摘要、构建工具版本和测试日志。Windows、Intel Mac 和 Docker 只有在对应环境验证之后才标记支持。旧成品可以直接恢复作为回退。

### C. 键盘、练习局和结算

**实施。** 在现有主菜单加「练习局」，复用设置、选将及对局入口。预设 2 人、简单 AI、固定的少量常见牌局面，依次验证「杀 → 闪」「结束出牌 → 弃牌」「胜负 → 结算」。练习默认可关闭出牌倒计时，经典身份局继续使用现有配置。复用 Textual 焦点、`Footer` 与现有弹窗，统一确认、取消和返回动作。现有数字键继续可用。超过十张手牌时提供键盘焦点移动与滚动，选中合法目标有清晰的焦点和选择状态。结算页复用 `GameOverScreen`，提供再来一局、返回主菜单和战报入口。

**改动文件。** `main_menu.py`、`game_setup.py`、`hero_select.py`、`game_play.py`、`game_over.py`、已有弹窗与样式、`i18n/` 和 `tests/test_pilot_ui.py`。先确定一个完整的练习预设，后续内容沿用它。

**验收。** 无鼠标走完「主菜单 → 练习局 → 选牌选目标 → 响应 → 结算 → 重开」。在 80×24 与 120×40 的实际终端中，当前操作、手牌、目标和结束回合入口可达；中英文分别验证。用 3–5 位首次接触本项目的玩家做一次试跑，目标为至少 4/5（5 人参与时）在 90 秒内完成第一次合法出牌。样本不足时记录实际人数、耗时和卡住步骤，作为下一次迭代依据。

### D. 战报与可复现对局

**实施。** 先通过已有 `EventBus` 将动作结果接到现有 `engine.action_log` 与 `MatchHistory`。同一局以唯一 ID 关联战绩与战报，写入格式版本、游戏版本、模式、玩家数、回合、阶段和动作结果。战报先展示玩家当时可见的事项，一局结束后保存完整结算摘要。旧 JSON 与 gzip 回放保持独立读取，CLI 入口按已知格式识别。存放路径使用同一个应用数据目录，同时保留旧位置用于读取。写入同目录临时文件，再原子替换，失败时保留旧战报。

引擎持有每局的随机数状态，优先迁移身份分配、牌堆洗牌、选将及 AI 决策，逐一检查技能和选牌的随机调用。用相同种子、同版本数据和相同动作序列复验。后续继续游戏只在安全阶段边界保存，需要确保存有牌区顺序、局级随机状态、回合临时状态及恢复入口。旧存档中不存在的数据沿用现有查询或回放能力。

**改动文件。** `game/events.py`、`game/engine.py`、`game/card.py`、`game/match_history.py`、`game/save_system.py`、`game/replay.py`、`tools/replay.py`、`main.py` 和结算页。

**验收。** 从正式界面赢或输一局，下一次启动能找到战报并对照胜负、回合和关键动作。两个同种子对局在独立进程及交替推进下生成相同的规则事件序列。坏文件或进程在写入中断时，已有战报仍可读。续局以后另行以「保存后继续一回合」对照「不中断继续」验证整局状态。

### E. AI 和内容维护

**实施。** 复用 `NormalStrategy` 的合法动作和回合上限。确认困难策略中的威胁评估实际参与选择后，再调权重。用同一批局面比较普通、困难 AI 的动作与胜率。内容维护以默认 `heroes.json`、技能注册表和卡牌定义为入口。启动或发布测试检查武将引用的技能是否注册、效果配置的目标类型是否合法、两套翻译是否键集一致，以及重复卡面定义是否有明确含义。先选 5 个常玩武将的具体技能验收，包括一次主动取消和一次响应。

**改动文件。** `ai/{normal_strategy,hard_strategy,strategy}.py`、`game/skills/registry.py`、`game/effects/registry.py`、`data/` 及现有自动对局或内容测试。赛事玩法、付费系统、额外素材与批量武将迁移留到独立需求。

**验收。** 使用已有 headless 测试按 2、4、8 人和三种难度运行固定种子矩阵，分别报告完成率、碰到回合或行动上限的比例、回合数分位值、身份分布和胜率。首轮验证为每人数、每难度 20 个种子，共 180 局。以当前版本建立基线，单独统计超时与达到上限的对局。重复摸牌用例仍稳定返回。

### F. 局域网双真人内测

**实施。** 先走一条「双真人进入同一房间、选将、连续出牌、响应、结算」的真实路径。房间连接和引擎座位建立明确对应，服务端用通过边界校验的动作对象提交共享引擎入口。同步数据按视角生成，服务器保留未公开身份、对手手牌和内部随机状态。声明房间的结束、断线和超时现有语义，重连后先送当前视角，再继续当前有效请求。首版走受控局域网。对外部署配置、会话真实性和房间任务生命周期独立验收。

**改动文件。** `net/{server,client,models,protocol,session}.py`、已有网络集成测试及本地接口的一处适配点。协议版本和断线策略落地前，README 标明当前联机体验状态。

**验收。** 两个真实客户端完成建房到胜负结算。可以在一次回合内连续提交合法动作。断线重连恢复玩家自己的手牌和当前请求。另一个玩家的私有信息未进入当前客户端快照。房间结束释放任务。验收通过后再决定是否加入正式版。

| 关卡 | 留存证据 |

| 游戏体验 | 记录首次合法出牌与整局耗时、卡住步骤、窄终端可操作性，决定默认练习预设与提示 |
